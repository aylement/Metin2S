1. SYNTHESE EXECUTIVE
================================================================================

[VERIFIE] SCENARIO A CONFIRME : le decouplage existe deja et fonctionne.

La classe joueur (PlayerEntity) ne depend que d'une INTERFACE de connexion
(IGameConnection : IConnection), jamais d'un socket concret. Le point d'envoi
de paquets est unique dans son contrat : IConnection.Send<T>(T packet)
(src/CorePluginAPI/IConnection.cs:12). Tous les ~68 sites d'envoi du serveur
de jeu passent par cette seule methode d'interface.

Preuve la plus forte : la suite de tests du depot cree DEJA un PlayerEntity
pleinement fonctionnel (spawn dans le monde, tick, mise a jour) avec un faux
IGameConnection genere par NSubstitute (aucun TcpClient, aucun socket) :
src/Tests/Game.Tests/WorldTests.cs:141-150. C'est exactement le patron
cmangos "disconnected/bot" decrit dans la demande, deja exerce par le code,
mais seulement pour des tests, pas pour un usage en production.

Le seul point de couplage fort au reseau est la classe concrete GameConnection
(src/Libraries/Game.Server/GameConnection.cs), qui herite de Connection
(src/Core/Core/Networking/Connection.cs), elle-meme un BackgroundService
attache a un TcpClient. Mais rien n'oblige a utiliser cette classe : un bot
n'a pas besoin d'heriter de Connection, il lui suffit d'implementer
IGameConnection directement (interface pure, 6 membres).

Effort de decouplage estime : FAIBLE A MOYEN.
- Le decouplage lui-meme (le sujet de l'etude) est deja fait par construction
  de l'architecture existante -> effort quasi nul pour "faire exister" un bot.
- L'effort reel se situe ailleurs : (a) fournir des donnees PlayerData/compte
  valides sans casser la persistance EF Core au despawn (risque identifie,
  section 11), (b) adapter le comportement (IBehaviour) car le systeme d'IA
  existant (SimpleBehaviour) est ecrit pour MonsterEntity et pas reutilisable
  tel quel sur un IPlayerEntity, (c) integrer proprement la creation/gestion
  du cycle de vie du bot dans PlayerFactory/World/GameServer.

Chemin le plus court : creer une classe NullGameConnection : IGameConnection,
une PlayerData en memoire, appeler PlayerFactory.CreatePlayerAsync, puis
IWorld.SpawnEntity. Detail section 10.

3. IPlayerFactory.CreatePlayerAsync (interface,
   src/Libraries/Game.Server/IPlayerFactory.cs:12) est implementee par

4. EnterGameHandler (src/Libraries/Game.Server/PacketHandlers/Loading/

   `_world.SpawnEntity(player)` : c'est l'insertion effective dans le monde
   simule (grille/quadtree, voir section 5).

[VERIFIE] Constructeur de PlayerEntity
(src/Libraries/Game.Server/World/Entities/PlayerEntity.cs:105-141) :
```
public PlayerEntity(PlayerData player, IGameConnection connection,
    IItemManager itemManager, IJobManager jobManager,
    IExperienceManager experienceManager, IAnimationManager animationManager,
    IQuestManager questManager, ICacheManager cacheManager, IWorld world,
    ILogger<PlayerEntity> logger, IServiceProvider serviceProvider)
```
Toutes les dependances hormis `player` (PlayerData, un DTO simple) et
`connection` sont des SERVICES ENREGISTRES DANS LE CONTENEUR DI et resolus
automatiquement par ActivatorUtilities -- un bot n'a donc besoin de fournir
explicitement QUE PlayerData et une implementation de IGameConnection ; le
reste est injecte normalement. Seul `player` est verifie non-null au
constructeur (`ArgumentNullException.ThrowIfNull(player)`, ligne 114) ;
`connection` n'est PAS verifie (voir section 4).

`LoadAsync()` (lignes 165-183) charge l'inventaire, la quickslot bar, calcule
MaxHp/MaxSp via IJobManager, charge les permissions, charge la guilde via

Toutes ces dependances viennent de services DI, aucune n'exige la connexion
reseau elle-meme -- seule IGameConnection.Server (IServerBase, interface) est
utilisee plus tard pour l'horodatage (`Connection.Server.Clock.Elapsed`,
ligne 1032, dans CalculatePlayedTimeAsync).

Il n'existe qu'une seule factory/methode de creation observee
(IPlayerFactory/PlayerFactory). Aucune autre voie de creation de PlayerEntity
en production n'a ete trouvee, hormis l'appel direct par
ActivatorUtilities.CreateInstance dans les tests
(src/Tests/Game.Tests/WorldTests.cs:148), qui contourne LoadAsync().


4. COUPLAGE A LA CONNEXION -- POINT CENTRAL
================================================================================

[VERIFIE] Type de la reference detenue par le joueur :
`public IGameConnection Connection { get; }` --
src/Libraries/Game.Server/World/Entities/PlayerEntity.cs:33.

[VERIFIE] IGameConnection est une INTERFACE, pas une classe concrete :
src/CorePluginAPI/IGameConnection.cs:7-15 :
```
public interface IGameConnection : IConnection
{
    IServerBase Server { get; }
    IPAddress BoundIpAddress { get; }
    Guid? AccountId { get; set; }
    string Username { get; set; }
    IPlayerEntity? Player { get; set; }
    bool HandleHandshake(GcHandshakeData handshake);
}
```
Elle herite de IConnection, elle-meme une interface pure
(src/CorePluginAPI/IConnection.cs:6-14) :
```
public interface IConnection
{
    Guid Id { get; }
    EPhase Phase { get; set; }
    Task? ExecuteTask { get; }
    void Close(bool expected = true);
    void Send<T>(T packet) where T : IPacketSerializable;
    Task StartAsync(CancellationToken token = default);
}
```
Aucun membre n'expose de type concret lie a un socket (pas de TcpClient, pas
de Stream). L'ensemble de la surface est implementable par une classe legere
qui n'a rien a voir avec le reseau. `Task? ExecuteTask` est nullable, ce qui
permet a une fausse connexion de n'avoir aucune tache d'execution associee.

[VERIFIE] La classe concrete de production, GameConnection, EST couplee a un
socket : elle herite de Connection (abstraite), elle-meme BackgroundService
lie a TcpClient/NetworkStream avec une boucle d'envoi degageant les paquets
d'une ConcurrentQueue vers le flux reseau
(src/Core/Core/Networking/Connection.cs:20-54, 134-214). Mais RIEN n'oblige
un bot a utiliser cette classe : PlayerEntity ne connait que l'interface
IGameConnection, jamais Connection ni GameConnection.

[VERIFIE] Nullabilite / deref sans verification :
- Le constructeur de PlayerEntity ne verifie PAS `connection` avec
  ArgumentNullException.ThrowIfNull (seul `player` l'est, ligne 114). Une
  connexion null casserait au premier `Connection.Send(...)` avec une
  NullReferenceException -- mais ce n'est pas un obstacle pour un bot,
  puisqu'on n'a pas besoin de null : on fournit une implementation "no-op".
- Le type `IPlayerEntity? Player` sur IGameConnection est nullable et deja
  traite comme tel partout observe (ex. EnterGameHandler.cs:26-32,
  CharacterMoveHandler.cs:33-38) : le code existant sait deja gerer une
  connexion sans joueur associe, ce qui est le sens inverse (utile si on
  veut, a terme, un bot qui n'a pas de PlayerEntity "reel" a certains
  moments), mais confirme la robustesse des verifications de nullite autour
  de IGameConnection.

[VERIFIE] Points d'envoi de paquets :
Recherche de `.Send(` dans src/Libraries/Game.Server : 68 occurrences dans
28 fichiers (ChatManager, handlers de paquets, Entity.cs, PlayerEntity.cs,
MonsterEntity.cs, SimpleBehaviour.cs, Shop.cs, Quest.cs, PlayerSkills.cs,
QuickSlotBar.cs, etc.). Ils sont DISPERSES dans la base (pas d'un seul point
d'appel), MAIS ils convergent tous vers UNE SEULE methode d'interface :
`IConnection.Send<T>(T packet)`. Il n'y a donc qu'UN SEUL POINT DE CONTRAT A
IMPLEMENTER, meme si les appelants sont nombreux. C'est la caracteristique clef
qui rend l'approche "connexion nulle absorbant les envois" viable a moindre
effort : une seule methode a rendre no-op.

Note complementaire : de nombreux appels a `.Send(...)` observes se font sur
`Connection.Send(...)` d'AUTRES joueurs (ex. `player.Connection.Send(packet)`
dans Entity.cs:308, 336, 383/434/439, SimpleBehaviour.cs:383,
CharacterMoveHandler.cs:92) -- c'est-a-dire qu'un bot recevra potentiellement
des paquets envoyes par le code quand il est dans la liste NearbyEntities
d'un vrai joueur ou l'inverse. Si le bot est le RECEVEUR (des vrais joueurs
lui envoient des paquets via son IGameConnection.Send), il faut absolument
que cette methode soit un no-op silencieux -- sinon exception.
Si le bot est l'EMETTEUR (bot.Connection.Send(...) est appele par du code qui
suppose que Connection est le joueur courant, ex. Entity.Die() ligne 340,
Respawn() ligne 383/387), le meme no-op suffit.

[VERIFIE] Verdict : on PEUT injecter une implementation "nulle" absorbant les
envois, et c'est deja fait pour les tests. Le point precis d'injection est le
parametre `connection` du constructeur de PlayerEntity / de
IPlayerFactory.CreatePlayerAsync(IGameConnection connection, PlayerData player)
(src/Libraries/Game.Server/IPlayerFactory.cs:12). Preuve d'usage reel dans le
code du depot lui-meme :
src/Tests/Game.Tests/WorldTests.cs:141-150 :
```
var conn = Substitute.For<IGameConnection>();
conn.BoundIpAddress.Returns(IPAddress.Loopback);
conn.Server.Returns(_gameServer);
var playerData = new PlayerData { Name = "TestPlayer", ... };
_playerEntity = ActivatorUtilities.CreateInstance<PlayerEntity>(_services,
    _world, playerData, conn);
_world.SpawnEntity(_playerEntity);
_world.Update(Tick(0.2)); // spawn all entities
```
Ce test cree un PlayerEntity complet, le spawn dans le World reel, et le fait
avancer dans la boucle de tick reelle -- sans aucun TcpClient. C'est
exactement le scenario demande dans le prompt (reference cmangos), deja
demontre fonctionnel dans ce depot, mais uniquement en contexte de test
unitaire, pas comme fonctionnalite de production exposee.

Limite identifiee (secondaire) : la connexion factice n'est PAS enregistree
dans `IGameServer.Connections` (ImmutableArray<IGameConnection>,
src/CorePluginAPI/IGameServer.cs:7), lequel n'est peuple que par
ServerBase<T>.OnClientAccepted (src/Core/Core/Networking/ServerBase.cs:88-89)
lors d'une vraie acceptation TCP. Or certains broadcasts globaux (chat)
passent par `gameServer.ForAllConnections(...)` qui itere
`gameServer.Connections`
(src/Libraries/Game.Server/Extensions/ConnectionExtensions.cs:7-14, utilise
dans ChatManager.cs:62,106,131). Consequence : un bot cree hors du flux TCP
n'apparaitra PAS dans cette liste et ne recevra donc pas les messages
diffuses par ce mecanisme precis -- sans impact pour l'objectif "faire
exister le bot", mais a garder en tete si un jour on veut que le bot recoive
des evenements globaux du serveur.


5. INSERTION DANS LE MONDE
================================================================================

[VERIFIE] Mecanisme COMMUN aux joueurs et aux monstres. `IWorld.SpawnEntity(
IEntity e)` (implemente dans World.cs:286-316) prend n'importe quel IEntity :
si c'est un IPlayerEntity, il l'ajoute au dictionnaire `_players` (AddPlayer,
ligne 305), puis dans tous les cas appelle `map.SpawnEntity(e)`
(Map.cs, methode publique non listee en detail ici mais qui enfile l'entite
dans `_pendingSpawns`, consommee par Map.Update, voir section 6).

[VERIFIE] Grille/index spatial : la carte (`Map`, classe concrete implementant
IMap) possede un QuadTree (`_quadTree`, src/Libraries/Game.Server/World/
Map.cs:41) commun a toutes les entites (joueurs, monstres, pierres metin,
objets au sol -- tous des IEntity). L'insertion se fait dans Map.Update() :
`_quadTree.Insert(entity)` (Map.cs:127), puis une requete de voisinage
`_quadTree.QueryAround(nearby, entity.PositionX, entity.PositionY,
Entity.VIEW_DISTANCE, filter)` (Map.cs:138) etablit les listes
NearbyEntities dans les deux sens (`entity.AddNearbyEntity(e)` /
`e.AddNearbyEntity(entity)`, Map.cs:142-143).

[VERIFIE] Visibilite : la portee de vue est une constante
`Entity.VIEW_DISTANCE = 10000` (src/Libraries/Game.Server/World/Entities/
Entity.cs:82). Le filtre de pertinence differencie : si l'entite qui bouge
n'est PAS un joueur, seuls les JOUEURS sont pertinents pour son "nearby"
(`filter = EEntityType.PLAYER`, Map.cs:131-136 et 187-192) -- optimisation
pour eviter de calculer les voisins de chaque monstre vis-a-vis d'autres
monstres. Quand une entite EST un joueur et que sa position a change
(`PositionChanged`), le code recalcule sa liste completement (Map.cs:184-231)
et notifie via `OnNewNearbyEntity`/`OnRemoveNearbyEntity`, qui pour
PlayerEntity declenchent `entity.ShowEntity(Connection)` /
`entity.HideEntity(Connection)` (PlayerEntity.cs:862-872) -- donc au final un
appel a Connection.Send(...). Un bot dont la connexion est no-op absorbera
silencieusement ces envois, exactement comme souhaite.

Le mecanisme est donc identique pour un joueur et pour un monstre (meme
QuadTree, meme classe Map, meme methode SpawnEntity/DespawnEntity) ; la seule
divergence de traitement est l'enregistrement optionnel dans le dictionnaire
`_players` de World (utile pour recherche par nom/vid, guildes, etc.).


6. BOUCLE DE MISE A JOUR
================================================================================

[VERIFIE] GameServer (src/Libraries/Game.Server/GameServer.cs) est un
BackgroundService dont la boucle de tick vise 100Hz : `_targetElapsedTime =
TimeSpan.FromTicks(100000)` = 10 ms (GameServer.cs:29, commentaire "100hz"
sur la meme ligne). La methode `Update(TickContext ctx)` (GameServer.cs:50-55)
appelle `EventSystem.Update(ctx)` puis `_world.Update(ctx)`.

[VERIFIE] World.Update (World.cs:185-193) parcourt toutes les cartes
chargees et appelle `map.Update(ctx)` pour chacune. Map.Update (Map.cs:121-234)
traite les spawns/despawns en attente PUIS appelle `entity.Update(ctx)` pour
CHAQUE entite de la carte (Map.cs:173-175), sans distinction entre joueurs et
monstres -- c'est le meme pipeline pour les deux.

[VERIFIE] Une entite se branche sur ce tick en surchargeant
`Entity.Update(TickContext ctx)` (methode virtuelle,
src/Libraries/Game.Server/World/Entities/Entity.cs:102-121). PlayerEntity la
surcharge pour la regeneration de vie/mana (PlayerEntity.cs:520-568),
MonsterEntity la surcharge pour la mort differee et pour piloter son
IBehaviour (`_behaviour?.Init/Update`, MonsterEntity.cs:102 et suite). Un bot
(qu'il soit une PlayerEntity standard ou une sous-classe) recevrait donc
NATURELLEMENT un appel a 100 Hz des lors qu'il est spawn dans une Map, sans
mecanisme special a batir : c'est deja le comportement de toute IEntity
inseree via IWorld.SpawnEntity.

Il n'existe pas de "timer independant par entite" observe (pas de
Timer/Task.Delay individuel par joueur/monstre pour son IA) : tout passe par
ce tick global synchrone a 100Hz. Un comportement de bot (deplacement, farm,
etc.) doit donc etre concu comme une machine a etats pilotee depuis
Update(ctx), a l'image de MonsterEntity + IBehaviour, et non comme une tache
asynchrone independante.


7. DEPLACEMENT ET DIFFUSION
================================================================================

[VERIFIE] Le chemin normal partant d'un paquet client est
CharacterMoveHandler (src/Libraries/Game.Server/PacketHandlers/Game/
CharacterMoveHandler.cs) : il valide le type de mouvement, verifie que
`ctx.Connection.Player` n'est pas null (lignes 33-38), puis pour un
deplacement standard appelle directement
`ctx.Connection.Player.Goto(ctx.Packet.PositionX, ctx.Packet.PositionY,
ctx.Connection.Server.Clock.Now)` (ligne 44) -- une METHODE PUBLIQUE ordinaire
de l'entite, PAS une methode privee au paquet. Puis il construit un paquet
CharacterMoveOut et le diffuse manuellement a chaque IPlayerEntity de
`ctx.Connection.Player.NearbyEntities` (lignes 88-94) via
`player.Connection.Send(movement)`.

[VERIFIE] Point d'entree interne existant : `Entity.Goto(int x, int y,
ServerTimestamp startAt)` (Entity.cs:135-175) et `Entity.Move(int x, int y)`
(Entity.cs:123-130, surchargee dans PlayerEntity.cs:239-264) sont des methodes
publiques de l'entite, appelables depuis N'IMPORTE QUEL code serveur, sans
paquet. La preuve la plus directe est SimpleBehaviour (systeme d'IA des
monstres) qui appelle `_entity.Goto(...)` directement en boucle
(World/AI/SimpleBehaviour.cs:252,271 notamment) pour deplacer une entite par
code pur, sans jamais passer par un paquet reseau. Un bot peut donc etre
deplace exactement de la meme maniere.

[VERIFIE] En revanche, la DIFFUSION du mouvement aux joueurs proches
(construction et envoi du paquet CharacterMoveOut) N'EST PAS centralisee dans
Entity/PlayerEntity elle-meme pour le cas "mouvement standard" -- c'est fait
manuellement dans le handler de paquet (CharacterMoveHandler.cs:74-94), donc
si un bot est deplace par du code interne (ex. un IBehaviour) sans passer par
ce handler, il faudra reproduire cette diffusion soi-meme (ou factoriser ce
bloc), sauf pour les monstres ou SimpleBehaviour.Update le fait deja pour les
attaques (SimpleBehaviour.cs:369-385) en construisant et envoyant lui-meme un
CharacterMoveOut aux joueurs proches. Il n'y a pas d'equivalent generique
"BroadcastMovement(entity)" reutilise par les deux chemins (packet-handler et
IA de monstre) -- chacun refait sa propre construction/diffusion du paquet.
C'est une duplication existante, pas une limite bloquante pour un bot, mais
un point a factoriser si on veut un bot "propre".


8. EXISTANT REUTILISABLE
================================================================================

[VERIFIE] Systeme d'IA pour les monstres :
- Interface IBehaviour (src/CorePluginAPI/Game/World/AI/IBehaviour.cs) avec
  `Init(IEntity entity)` et `Update(TickContext ctx)`.
- SimpleBehaviour (src/Libraries/Game.Server/World/AI/SimpleBehaviour.cs) :
  agressivite (`IsAggressive`, ligne 40, activee via `EAiFlags.AGGRESSIVE` du
  proto monstre, ligne 74), ciblage/aggro avec table de degats
  (`_damageMap`, TookDamage/NextTarget, lignes 388-442), deplacement
  aleatoire en idle (MoveToRandomLocation, lignes 85-101), poursuite et
  positionnement d'attaque avec verification d'obstacles via l'attribut de
  carte (TryGoto verifie BLOCK/OBJECT et ligne droite, lignes 243-273),
  gestion de la portee d'attaque et du cooldown (Update, lignes 146-241).
  C'est une machine a etats assez complete, mais ECRITE POUR IEntity
  generique cote mouvement (donc reutilisable pour deplacer un bot-joueur),
  MOTIF PARTIELLEMENT SPECIFIQUE A MonsterEntity cote attaque : `Attack(...)`
  caste explicitement `_entity is not MonsterEntity monster` et retourne sinon
  (SimpleBehaviour.cs:359-362), et `ShouldChangeAttackPosition`/`MoveTo`
  utilisent aussi des checks `is MonsterEntity` (lignes 124, 316). Donc :
  reutilisable pour le DEPLACEMENT d'un bot, PAS directement reutilisable
  tel quel pour le COMBAT d'un bot-joueur sans modification (petit
  refactoring pour generaliser au-dela de MonsterEntity, ou nouvelle classe
  de comportement dediee aux bots-joueurs en s'inspirant de SimpleBehaviour).
- StoneBehaviour (src/Libraries/Game.Server/World/AI/StoneBehaviour.cs) :
  comportement specifique aux pierres Metin, non pertinent pour des bots.
- Pas de pathfinding au sens "recherche de chemin" (A*, navmesh) observe --
  uniquement des trajectoires directes avec verification d'obstacle en ligne
  droite (`IsAttrOnStraightPathTo`, utilise par SimpleBehaviour.cs:266).

[VERIFIE] Outils/commandes qui creent des entites par code (donc sans passer
par un paquet client) :
- SpawnCommand (src/Libraries/Game.Server/Commands/SpawnCommand.cs:35-66) :
  commande GM `/spawn` (alias `/m`, `/mob`) qui instancie directement
  `new MonsterEntity(...)` puis `_world.SpawnEntity(monster)` -- c'est le
  PATRON DIRECT a suivre pour une future commande "spawn bot".
- SpawnExtendedCommand, SpawnMapRandomCommand : variantes non detaillees ici,
  meme famille.
- Le test WorldTests (section 4) constitue un deuxieme patron directement
  transposable pour un joueur (et non un monstre).

Aucun autre outil de debug specifique aux "faux joueurs" n'a ete trouve dans
le depot (pas de commande "bot", "fakeplayer" ou equivalent).

[VERIFIE] Persistance au despawn : PlayerEntity.OnDespawnAsync appelle

PlayerEntity pour le combat (casts explicites vers MonsterEntity, section 8)
-- un comportement de bot-joueur devra etre ecrit specifiquement, meme s'il
peut reutiliser une bonne partie de la logique de mouvement/aggro par
copie/adaptation plutot que par reutilisation directe de la classe.

[VERIFIE] Duplication de la diffusion de mouvement (section 7) : si un bot
est deplace par du code custom hors du chemin CharacterMoveHandler, il faut

[HYPOTHESE] Le systeme de plugins (Weikio.PluginFramework, ExamplePlugin/

[HYPOTHESE] Handshake et cycle de connexion : IGameConnection expose

13.3 BUGS REELS TROUVES ET CORRIGES DANS LE SERVEUR DE BASE
--------------------------------------------------------------------------
Quatre bugs preexistants, sans rapport avec la faisabilite des bots en soi,
ont ete decouverts en testant le premier bot en conditions reelles -- ils
auraient touche n'importe quel VRAI joueur dans les memes circonstances :

1. PlayerSkills.cs (4 sites) : la garde
   `_player.Player.SkillGroup.IsDefined()` est censee verifier "le joueur a
   choisi une branche de competences", mais ESkillGroup.UNKNOWN=0 est
   lui-meme un membre "defini" de l'enum -- la garde ne filtrait donc jamais
   rien. Resultat : IndexOutOfRangeException dans
   AssignDefaultActiveSkills() pour TOUT personnage fraichement cree (niveau
   1, branche pas encore choisie), bot ou reel. Corrige via une methode
   HasChosenSkillGroup() qui exclut explicitement UNKNOWN.

2. Map.cs, boucle de despawn (Update()) : entity.Dispose() etait appele
   AVANT le retrait de l'entite du QuadTree et des listes NearbyEntities des
   autres joueurs. Si Dispose() levait une exception (observe : une race
   Microsoft.Data.Sqlite lors d'une reconnexion quasi simultanee,
   "Collection was modified" dans DisposePreparedStatements), le reste du
   nettoyage ne s'executait jamais -- le personnage restait visible
   indefiniment comme un fantome fige pour tous les autres joueurs. Corrige
   en reordonnant (nettoyage du monde d'abord) et en encadrant Dispose()
   d'un try/catch qui log sans jamais bloquer le nettoyage.

3. QuickSlotBar.PersistAsync() fait un `_db.Players.FirstAsync(x => x.Id ==
   Player.Player.Id)` -- leve pour un bot (Id=0, aucune ligne en base).
   Contrairement a DbPlayerRepository.SetPlayerAsync/GetPlayerAsync (qui se
   degradent proprement -- no-op / null -- pour un Id inexistant, verifie),
   ce chemin plante dur. Solution retenue : les bots ne persistent jamais du
   tout (OnDespawnAsync et LoadAsync surcharges dans BotPlayerEntity pour
   sauter la persistance), plutot que de fiabiliser QuickSlotBar pour le cas
   general.

4. PlayerExtensions.SendCharacter envoyait Angle=0 en dur dans le paquet
   SpawnCharacter au lieu de la vraie Rotation de l'entite (comparer
   MonsterEntity.ShowEntity, qui envoie correctement Angle=Rotation).
   Corrige. N'a PAS resolu le bug d'animation decrit en 13.4.

13.4 LIMITE NON RESOLUE : ANIMATION D'ATTAQUE
--------------------------------------------------------------------------
[VERIFIE] Envoyer un paquet CharacterMoveOut avec MovementType=ATTACK ou
COMBO fige DEFINITIVEMENT le rendu du bot cote client reel observateur : le
personnage se bloque sur place, tourne seulement, cesse de recevoir toute
mise a jour de position (le serveur continue de le deplacer, le client
affiche une position perimee). Confirme par elimination en direct avec
l'utilisateur : ni le "lunge" (pas en avant avant le coup), ni la valeur
d'Argument du combo, ni l'equipement n'en sont la cause -- desactiver
purement et simplement l'envoi de ce paquet restaure un mouvement fluide
normal (juste sans animation de coup visible).

Deux sources originales ont ete extraites et lues pour investiguer (voir
memoire persistante [[client-server-original-source]] pour les chemins
exacts) :
- Client C++ original (ClientVS22.zip, UserInterface/InstanceBase.cpp) :
  confirme que FUNC_ATTACK/FUNC_COMBO sont bien geres par une machine a
  etats qui, si la position cible est a >=50 unites, fait d'abord marcher
  le personnage puis joue le coup ; et confirme que c'est CHAQUE CLIENT
  OBSERVATEUR qui choisit l'animation exacte a partir de ses propres
  donnees de mouvement par race/arme, en utilisant seulement l'octet
  Argument comme numero d'etape -- le bot n'a donc pas besoin de connaitre
  l'ID d'animation exact.
- Serveur C++ original (metin2_server+src.tar.gz,
  server/game/src/char_battle.cpp/battle.cpp) : confirme qu'il n'existe
  AUCUNE logique de cone/splash cote serveur, meme pour un vrai joueur --
  CHARACTER::Attack ne traite qu'une victime a la fois ; le cone visuel
  vient entierement du client, qui envoie un paquet Attack par cible
  touchee. Ceci valide l'approche cote bot (section 13.1) comme etant
  l'equivalent correct.

Malgre cette lecture, la structure du paquet envoye par le bot correspond a
ce que le code source original attend -- la cause exacte du figement n'a
pas ete identifiee. Hypotheses non testees : version de protocole
differente entre ce build client precis et celui vise par ce depot, champ
ou paquet complementaire manquant ailleurs dans le flux (CharacterInfo ?
un etat prealable requis ?), ou incompatibilite specifique a ce build.
Necessite soit un outil de debug cote client (non disponible ici), soit une
comparaison paquet-par-paquet avec une capture reseau d'un vrai combo joue
par un vrai joueur.

Etat actuel : l'envoi du paquet d'animation d'attaque est desactive dans
BotPlayerEntity.cs (code laisse en place et documente, pas supprime) --
comportement stable, bot pleinement fonctionnel sans swing visible.

17.2 BUG TROUVE : FUITE DES ENREGISTREMENTS D'EVENEMENTS DE QUETE

--------------------------------------------------------------------------
Symptome rapporte par l'utilisateur : en parlant au palefrenier et en
choisissant "Horse Trial", des bandes noires (letterbox) apparaissent en
haut/bas de l'ecran et le client reste bloque, injouable (Echap, quitter,

Premiere piste exploree (et ecartee apres verification complete) : un bug
dans le tokenizer du client pour les balises [QUESTION ...]. Le parser reel
a ete retrouve et lu integralement dans les sources client d'origine
(EterLib/parser.h + parser.cpp, fonction Group::GetArg) : le format
"1;Start the trial|2;Not now" genere par Quest.ChoiceAsync() est en fait
correctement gere -- les espaces internes aux libelles sont bien preserves
par ce parser (seul un espace juste apres un "|" ou en tout debut est
ignore). Verifie caractere par caractere sur l'exemple reel. Ce n'etait

Cause reelle trouvee en remontant QuestManager.InitializePlayer : cette
methode est appelee a CHAQUE PlayerEntity.LoadAsync() -- c'est-a-dire a
chaque connexion reelle ET a chaque /botspawn -- et re-enregistre a chaque
fois les gestionnaires de clic/don/kill de TOUTES les quetes via Quest.
Init() dans les dictionnaires STATIQUES de GameEventManager
(NpcClickEvents, NpcGiveEvents, desormais aussi MonsterKillEvents). Rien ne
nettoyait jamais les anciens enregistrements : BotPlayerEntity.
OnDespawnAsync() court-circuitait meme entierement la logique de despawn
(y compris ce nettoyage) pour eviter un crash de persistance different (cf.
section anterieure du rapport). Avec le nombre de cycles /botspawn +
/botdespawn et de reconnexions de cette session, NpcClickEvents[20349] a
accumule un grand nombre d'entrees "Horse Trial" dupliquees, chacune liee
par fermeture (closure) a un IPlayerEntity obsolete/mort. Les Vid (id de
session) etant reutilises apres depart d'un joueur/bot, un clic pouvait
alors correspondre a plusieurs entrees perimees a la fois -- ce qui
declenche cote serveur un menu de desambiguisation
(InternalQuest.SelectQuestAsync) : c'est tres probablement ce que
l'utilisateur a vu en "choisissant Horse Trial" (parmi plusieurs entrees
dupliquees), et invoquer un callback lie a un joueur/connexion mort est ce
qui a fige le client.

1. Ajout d'un champ uint? PlayerVid explicite sur les 3 structures
   d'evenement de GameEventManager (null reserve aux enregistrements
   veritablement globaux comme les boutiques PNJ, qui ne doivent jamais
   etre balayes par le nettoyage).
2. Nouvelle methode GameEventManager.UnregisterPlayer(uint vid) qui retire
   toutes les entrees de ce Vid dans les 3 dictionnaires.
3. Appelee au debut de QuestManager.InitializePlayer (couvre un Vid
   reutilise dont le proprietaire precedent n'a pas proprement quitte) ET
   depuis PlayerEntity.OnDespawnAsync / BotPlayerEntity.OnDespawnAsync
   (couvre un depart normal -- les bots nettoient desormais leurs
   evenements de quete au despawn, meme s'ils sautent toujours la
   persistance en base).

Lecon generale pour ce depot : tout enregistrement par-joueur dans une
collection static doit avoir un chemin de nettoyage par-joueur symetrique ;
et un override "skip persistence" trop large sur un bot (comme
OnDespawnAsync() => Task.CompletedTask) peut faire sauter d'autres
nettoyages non lies a la persistance sans que ce soit voulu.

Build + serveur relance avec le correctif (dotnet build sur Game.Server,
Executables/Single et Game.Tests tous verts). En attente de re-test par
l'utilisateur : parler au palefrenier (NPC 20349), lancer "Horse Trial",
confirmer que le menu de choix est propre (2 options seulement) et que le

27d. VRAI BUG TROUVE ET CORRIGE : persistance de position en course avec une
     ecriture DB concurrente plus ancienne
--------------------------------------------------------------------------
Le correctif de PlayerEntity.Warp() de plus tot dans la soiree (persister la
position avant de deconnecter le client pour un saut inter-map) utilisait un
appel fire-and-forget (sans attendre sa completion). Sans attente explicite,
rien ne garantit qu'il se termine avant un appel de persistance ULTERIEUR et
sans rapport (ex : un /shutdown quelques secondes plus tard) -- si le
deuxieme appel (plus recent, position correcte) se termine avant le premier
(plus ancien, fire-and-forget, position perimee), le second ecrase le
resultat du premier avec une valeur perimee. Confirme en direct :
l'utilisateur s'est retrouve reconnecte sur "une position precedente, mais
pas la derniere" -- exactement le symptome attendu d'une telle course.

Corrige en rendant cet appel bloquant (attente synchrone explicite, avec
suppression ciblee de l'avertissement d'analyseur correspondant -- meme
motif deja utilise ailleurs dans World.cs pour une raison similaire) plutot
que de rendre Warp()/Move() asynchrones (ce qui aurait necessite de modifier
la signature de IEntity.Move et tous ses appelants). Une teleportation
inter-map est une operation rare, pas un chemin critique en frequence, donc
un court blocage est un compromis acceptable pour garantir l'ordre des
ecritures.

29. REGRESSION APRES LE REMPLACEMENT DE SKILLTABLE.TXT : AURA ET BERSERKER
    AVAIENT PERDU LEUR AURA/ICONE DE BUFF -- VRAI BUG DE PARSING TROUVE ET
    CORRIGE
================================================================================
Date: 2026-08-22 (matin)

Suite au remplacement de skilltable.txt par la vraie copie du client
(section 27c), l'utilisateur a signale : plus d'aura autour de l'arme, plus
d'icone de buff en haut a gauche, pour Aura du Sabre ET Berserker Fury.

Cause : le fichier client encode les colonnes AffectFlag/AffectFlag2 en
INDEX DE BIT NUMERIQUE (ex: "15" pour Aura) alors que l'ancien fichier de ce
repo utilisait des NOMS TEXTE lisibles (ex: "GEOMGYEONG"). Confirme par
correspondance exacte : EAffectFlags.GEOMGYEONG = 1 << 15, JEONGWIHON =
1 << 14, CHEONGEUN = 1 << 16 -- les nombres du fichier client (14/15/16)
correspondent pile aux montants de decalage de bit de ces memes noms. La
fonction ParserService.ExtractAffectFlags() ne savait faire correspondre
que des NOMS d'enum (via EnumUtils.TryParseEnum), donc chaque valeur
numerique echouait silencieusement (aucune correspondance de nom trouvee) et
le flag retombait a 0 -- 15 sorts sur 77 sont concernes (au moins un sort
actif buff par classe/branche), pas seulement Aura et Berserker.

Important a noter : le BONUS DE STAT lui-meme (vitesse d'attaque, defense,
etc.) continuait de s'appliquer normalement cote serveur -- seul le paquet
AffectAdd envoye au client avec Flag=0 empechait l'icone de buff et l'aura
visuelle de s'afficher, purement cosmetique mais evidemment tres genant
pour juger si un sort "marche".

Corrige : ExtractAffectFlags() essaie maintenant de parser la valeur comme
un entier d'abord (traite alors comme un index de bit, `1 << N`), et ne
retombe sur la correspondance par nom que si ce n'est pas un nombre. "0" est
traite comme NONE (pas comme le bit 0/YMIR) par securite. Confirme en
direct par l'utilisateur apres redeploiement : "the buff and aura are back."

30. BONUS DE DEGATS "PLACEHOLDER" CONTRE LES MONSTRES -- fonction
    CalculateAttackBonus() etait un no-op complet (todo jamais fait)
================================================================================
Date: 2026-08-22 (matin)

L'utilisateur a fourni un point de comparaison concret : un personnage
niveau 55 boost sur un vrai serveur officiel (video de 2010) tapait un
metin pour 1500 dommages, alors qu'Admin (niveau 99, 249 STR, arme deux
mains "75+9") ne tape qu'environ 800 -- meme apres la correction ATTACK_GRADE
de cette nuit (section 27a).

Verifie contre le vrai CalcMeleeDamage()/CalcAttBonus() (battle.cpp,
source serveur original) : la structure de formule de ce repo correspond
EXACTEMENT au vrai code (meme calcul de degats d'arme, meme attackRating,
meme ordre d'operations) -- sauf un morceau completement absent :
Entity.CalculateAttackBonus() est un no-op integral, avec des commentaires
"todo implement bonus attack against animals etc..." jamais traites. Le
vrai CalcAttBonus() applique plusieurs bonus en POURCENTAGE a ce niveau,
notamment POINT_ATTBONUS_MONSTER (bonus general contre tout ce qui n'est
pas un joueur, metins inclus) et des bonus specifiques par race
(animal/mort-vivant/humain/etc.).

Probleme de fond : dans le vrai jeu, ces pourcentages proviennent des
ATTRIBUTS D'OBJETS (affixes aleatoires sur l'equipement, ex: "+15% degats
contre les monstres") -- un systeme ENTIER absent de ce repo (chaque objet
ici est un proto statique fixe, aucune valeur d'attribut par instance
n'existe nulle part dans le code). Le joueur de la video avait tres
probablement plusieurs de ces bonus cumules sur son equipement reel, jamais
modelisable ici sans construire tout ce sous-systeme.

Decision de l'utilisateur (question posee explicitement) : plutot que de
laisser ce trou tel quel OU de construire le systeme d'attributs complet,
implementer un bonus fixe ("placeholder") pour tester rapidement. Applique :
CalculateAttackBonus() ajoute desormais +20% de degats quand la cible n'est
PAS un joueur (MONSTER/METIN_STONE/NPC/etc., toute cible non-PLAYER et
non-POLYMORPH_PLAYER) -- une constante codee en dur
(PlaceholderMonsterDamageBonusPercent = 20), PAS une vraie donnee par objet,
documentee comme telle dans le code, a remplacer si un jour un vrai systeme
d'attributs existe (GetPoint(EPoint.ATTBONUS_MONSTER) reel).

Non teste en direct au moment de la redaction -- +20% seul ne comblera
probablement pas tout l'ecart avec les 1500 degats de la video (l'utilisateur
a lui-meme reconnu "there are multiple issues to resolve"), a retester et
ajuster.
